The reward is the specification

The question

Can we reward the reasoning we are able to check, rather than the answer we hope for?

A reward is a specification, whether or not it was written as one. Reward the final answer and the specification reads produce the string that matches — which a model can satisfy by becoming an excellent guesser. Reward a verifier’s verdict and it reads produce reasoning that survives checking, which is much harder to satisfy by accident. That is the whole reason the first leg of the loop cares so much about whether an answer is checkable: a benchmark that can be audited is also a reward that can be trusted.

Three places where this turns out to bite harder than expected:

  1. Who teaches, and how loudly. Choosing a teacher per domain is not the same as deciding how much that teacher’s feedback should count.
  2. Which verifier picks the winner. Best‑of‑K is only as good as the thing doing the selecting, and the best selector is not the same for every generator.
  3. How much human prior is actually needed. In formal verification the hand‑written scaffolding is substantial; RL lets you ask which of it was load‑bearing.

Ordered by what each one shows, not by date. Dates, venues and full author lists are on the Record.

The experiments

What has been run

    2026 1st of 9

    Label routing decides which teacher supervises a prompt, but not how strongly that teacher’s feedback counts. Normalising the feedback scale per domain adds 1.2–3.1 points over label routing, and it does so consistently across 2B, 4B and 9B students.

    Beyond Teacher Assignment: Domain‑Normalized Multi‑Teacher On‑Policy Distillation

Compose

A verifier that picks well for one model is a component. Several models talking to each other is a system, and systems have behaviours their parts do not. When several models work together, does the interaction help, or quietly destroy answers that were already right?
